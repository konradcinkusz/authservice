# Security Policy

AuthService is an authentication service. If it has a vulnerability, the consequences land on
whoever deployed it and on their users — so please report problems privately and give us a
chance to fix them before they are public.

## Reporting a vulnerability

**Use GitHub Private Vulnerability Reporting:**
[Report a vulnerability](https://github.com/konradcinkusz/authservice/security/advisories/new)

That channel is private between you and the maintainers, and it lets us publish a coordinated
advisory when a fix ships.

Please do **not** open a public issue for a suspected vulnerability. If private reporting is
unavailable to you for any reason, open a public issue that says only "security report,
please provide a private contact" with no details.

### What to include

- What the issue is and which component it affects (endpoint, service, configuration).
- How to reproduce it — a `curl` sequence is ideal.
- What an attacker gains: account takeover, privilege escalation, data disclosure, denial of
  service.
- The version or commit you tested, and any relevant configuration.

## What to expect

| Stage | Target |
| --- | --- |
| Acknowledgement of your report | 5 working days |
| Initial assessment (valid / not / need more information) | 10 working days |
| Fix or documented mitigation for a confirmed high-severity issue | 30 days where practical |

This is a volunteer-maintained project, not a company with an on-call rota. Those are honest
targets rather than a contractual SLA, and we would rather say so than publish numbers we
cannot hold to.

We will credit you in the advisory unless you ask us not to.

## Supported versions

| Version | Supported |
| --- | --- |
| `main` | Yes |
| Latest tagged release | Yes |
| Older tags | No |

Fixes land on `main` and in the next release. There is no long-term support branch.

## Scope

**In scope** — anything in this repository: the ASP.NET Core service, its Dockerfile, the
GitHub Actions workflows, the Fly.io deployment configuration, and the documented
configuration defaults.

**Out of scope**

- Vulnerabilities in dependencies, unless this project's usage is what makes them exploitable.
  Report those upstream; tell us if we should pin or work around them.
- Findings that require a configuration the documentation explicitly warns against — for
  example `Auth:AllowTokensInOAuthRedirect`, `Auth:RequireVerifiedProviderEmail=false`, or
  `Network:TrustAllProxies=true` on a directly reachable host. Those switches exist as
  documented escape hatches with their consequences stated.
- Missing hardening headers or a missing rate limit on an endpoint, absent a concrete attack.
- Reports generated by a scanner with no analysis of whether the finding is reachable here.

## Known posture

Be aware of the following when evaluating this project:

- **It has not had an external security audit.** No third party has reviewed this code.
- **Tokens are signed with a symmetric HS256 key** shared with every service that validates
  them, which means every such service can also mint tokens. Whether to move to RS256 with a
  JWKS endpoint is tracked in the issue backlog.
- **The demo deployment and `docker-compose.yml` ship deliberately weak, publicly documented
  credentials.** They are for evaluation. Do not point anything real at them.
- **With no email provider configured, email is not sent at all.** The fallback logs that a
  message was skipped; it writes the token itself only in Development. A deployment that never
  sets `SendGrid:ApiKey` therefore has no working password-reset or verification flow — which
  is why email verification stays off in that configuration rather than locking users out.
- Security-relevant configuration is summarised in the service's startup log line, so you can
  confirm from the logs which posture a deployment actually came up in.
